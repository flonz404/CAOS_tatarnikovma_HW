# HW3. Моделирование гостиницы с помощью процессов

**Дисциплина:** АКОС.

**Выполнил:** Татарников Максим Александрович, БПИ-252.

**Вариант:** №12 – Задача о гостинице.

**Реализованный уровень:** 8 баллов. Сохранены решения на 4–5 и 6 баллов.

## 1. Условие задачи

В гостинице есть ограниченное количество одноместных номеров. Клиенты прибывают через случайные интервалы и запрашивают номер на заданное число суток. Если свободных номеров нет, клиент встаёт в очередь. После выезда одного гостя администратор заселяет следующего.

Программа показывает прибытие, запрос номера, очередь, назначение номера, заселение, каждые завершённые сутки и выезд. Один номер занимает не более одного клиента, а клиент занимает не более одного номера.

## 2. Варианты реализации

| Уровень | Программы | Организация работы |
| --- | --- | --- |
| 4–5 | `hotel` | Родитель создаёт администратора и клиентов через `fork`. Используются именованные POSIX-семафоры. |
| 6 | `hotel_unnamed` | Та же модель с неименованными POSIX-семафорами в общей памяти. |
| 7–8 | `hotel_manager`, `hotel_admin`, `hotel_client` | Программы запускаются отдельно и подключаются по имени гостиницы. Используются именованные POSIX-семафоры. |

Во всех вариантах данные гостиницы находятся в разделяемой памяти POSIX. Программы написаны на C на основе предыдущего задания.

| Участник | Его работа |
| --- | --- |
| Координатор | Читает данные, отсчитывает сутки, следит за завершением и сохраняет результат. |
| Администратор | Обрабатывает очередь и назначает свободные номера. |
| Каждый клиент | Запрашивает номер, ожидает, заселяется, проживает заданный срок и выезжает. |

В первых двух вариантах участники являются дочерними процессами. В третьем координатор не создаёт другие процессы: администратор и каждый клиент запускаются отдельной командой. Их завершение подтверждается через общую память, а `waitpid` для них координатор не использует.

## 3. Работа модели

Номера, клиенты, очередь и счётчики хранятся в `SharedState`. Общая память создаётся через `shm_open`, `ftruncate` и `mmap` с `MAP_SHARED`.

Семафор `ROOM_LOCK` защищает общие данные. Отдельные семафоры уведомляют администратора и клиентов о событиях. Счётчик `pending_work` позволяет перейти к следующим суткам только после обработки текущих событий.

Правила гостиницы одинаковые во всех версиях:

- Время начинается с нуля. Интервал 0 допускает одновременное прибытие.
- Заселение происходит по очереди (FIFO). При одновременном прибытии учитывается фактический порядок постановки в очередь.
- Очередь вмещает всех клиентов.
- Принимаются клиенты, прибывшие строго раньше момента закрытия приёма.
- После закрытия приёма очередь продолжает обслуживаться.
- Ожидание не входит в срок проживания. При обычном завершении каждый заселённый клиент проживает весь заказанный срок.

В независимом варианте координатор создаёт ресурсы сеанса, а остальные программы открывают их по имени. Указатели в общую память не записываются. Один номер клиента может подключиться только один раз; администратор также может быть только один.

Отсчёт суток начинается после подключения администратора и всех клиентов. Подключение программы ещё не означает прибытие клиента: оно произойдёт в назначенные условные сутки. Участники могут подключаться в любом порядке после запуска координатора.

Все события независимого варианта выводятся в терминале координатора. Клиенты и администратор записывают сообщения в общую память, а координатор выводит их после обработки событий суток.

## 4. Ввод, сборка и запуск

Все команды ниже выполняются из папки `HW3`. Данные вводятся с клавиатуры или читаются из файла:

| Параметр | Допустимые значения |
| --- | --- |
| Количество номеров | 1–100 |
| Количество клиентов | 1–100 |
| Минимальный интервал прибытия | 0–10000 суток |
| Максимальный интервал прибытия | От минимального до 10000 суток |
| Момент прекращения приёма | 1–10000 суток |
| Задержка между условными сутками | 0–5 реальных секунд |
| Срок проживания каждого клиента | 1–10000 суток |

Сборка всех доступных вариантов через CMake:

```sh
cmake -S . -B build
cmake --build build
```

Исполняемые файлы появятся в `build`. В Linux собираются все пять программ. В macOS собираются `hotel` и три независимые программы; `hotel_unnamed` требует Linux, так как `sem_init` в macOS не поддерживается.

Для сборки через GCC в Linux:

```sh
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread hotel.c -o hotel -lrt
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread hotel_unnamed.c -o hotel_unnamed -lrt
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread independent/manager.c independent/hotel.c -o hotel_manager -lrt
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread independent/administrator.c independent/hotel.c -o hotel_admin -lrt
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread independent/client.c independent/hotel.c -o hotel_client -lrt
```

На macOS нужно убрать `-lrt` и пропустить сборку `hotel_unnamed`.

Запуск первых двух вариантов после сборки через GCC:

```sh
./hotel < tests/test_cutoff.txt
./hotel_unnamed < tests/test_cutoff.txt
```

Для независимого варианта в первом терминале:

```sh
./hotel_manager demo < tests/test_cutoff.txt
```

После сообщения «Гостиница demo готова к подключениям» во втором терминале из той же папки:

```sh
./hotel_admin demo &
./hotel_client demo 1 &
./hotel_client demo 2 &
./hotel_client demo 3 &
wait
```

`&` запускает программу в фоне, а `wait` ждёт завершения запущенных программ. Их также можно запускать по отдельности в разных терминалах. После сборки через CMake вместо `./hotel_manager` и остальных имён используется `./build/hotel_manager` и соответствующие пути.

`demo` – общее имя сеанса. Допускаются 1–12 латинских букв, цифр или символов `_`. Для одновременных запусков нужны разные имена. Повторный координатор с занятым именем завершится с ошибкой, не затрагивая работающую гостиницу.

По умолчанию координатор ждёт подключения участников 60 секунд. Необязательный второй аргумент меняет ожидание в пределах 1–300 секунд:

```sh
./hotel_manager demo 120 < tests/test_cutoff.txt
```

Если запустились не все участники, координатор завершает сеанс с ошибкой. Запуск клиента или администратора до готовности координатора выдаёт понятное сообщение.

## 5. Завершение и очистка

Программа завершает работу, когда все принятые клиенты выехали, а остальные уже не могут быть приняты. При наличии очереди обслуживание продолжается после закрытия приёма. Если всех обслужили раньше, завершение происходит досрочно.

Для остановки используются Ctrl+C (`SIGINT`) и `SIGTERM`. В независимом варианте сигнал можно отправить координатору или любому подключённому участнику. Клиент или администратор передаёт запрос координатору, который останавливает весь сеанс. При ошибке участника моделирование также прекращается.

В вариантах с `fork` родитель собирает детей через `waitpid`. В независимом варианте участники записывают подтверждение завершения в общую память; их процессы собирает оболочка или программа, из которой они были запущены. Ожидание блокировки и обработки суток ограничено, чтобы при сбое не зависнуть навсегда.

Имена семафоров и общей памяти удаляет создавший их координатор. Каждый участник закрывает свои семафоры и отображение памяти. В варианте с неименованными семафорами родитель вызывает `sem_destroy` после завершения детей. При частичной ошибке создания удаляются только успешно созданные ресурсы.

Итог выводится в консоль. Первые две программы сохраняют его в `hotel.log`, независимая версия – в `hotel_<имя>.log`, например `hotel_demo.log`. При прерывании сохраняется текущее состояние гостиницы. Если из-за аварии потерян доступ к общим данным, в лог записывается сообщение об ошибке вместо недостоверной статистики.

Коды завершения: `0` – успех, `1` – ошибка, `130` – `SIGINT`, `143` – `SIGTERM`. При неверном вводе модель не запускается. Неперехватываемый `SIGKILL` координатора не является штатным способом остановки; очистка ресурсов в этом случае не гарантируется.

## 6. Проверка работы

Для тестов нужны компилятор и Python 3. Запуск всех поддерживаемых вариантов:

```sh
sh run_tests.sh
```

Можно выбрать отдельный вариант:

```sh
sh run_tests.sh named
sh run_tests.sh unnamed
sh run_tests.sh independent
```

Результаты проверки 8 ноября 2026 года:

| Вариант | Linux ARM64, GCC | macOS ARM64, Apple clang |
| --- | --- | --- |
| Именованные семафоры и `fork` | 57 проверок пройдены | 56 проверок пройдены |
| Неименованные семафоры и `fork` | 58 проверок пройдены | Не поддерживается |
| Независимые программы | 57 проверок пройдены | 57 проверок пройдены |

Сборка через CMake проверена с `-Wall -Wextra -Wpedantic -Werror`. Проверка дочерних PID через `/proc` выполняется только в Linux.

Тесты проверяют очередь, одновременные прибытия и выезды, полный срок проживания, границу приёма, большие значения, неправильный ввод и итоговую статистику. Для независимых программ дополнительно проверены:

- подключение клиентов раньше администратора;
- запрет повторного подключения участника и запуска второго координатора с тем же именем;
- отсутствие администратора или клиента и истечение времени ожидания;
- остановка через сигнал координатору, администратору или клиенту;
- аварийное завершение участника;
- два параллельных сеанса и повторное использование имени после завершения;
- запуск участников из разных папок;
- ошибки создания памяти, семафоров, подключения и записи лога;
- отсутствие оставшихся IPC-ресурсов после завершения.

Проверка событий общая для всех трёх вариантов. Например, в `test_cutoff` первый клиент живёт с суток 1 до суток 4, второй ждёт и живёт с суток 4 до суток 5. Третий прибывает ровно в момент закрытия приёма и не принимается. Результат всех вариантов:

```text
Моделирование завершено на сутках: 5
Всего приняли клиентов: 2.
Полностью завершили проживание: 2.
Не успели принять клиентов: 1.
Ожидают заселения: 0.
Занятых номеров: 0.
```

Примеры граничных тестов:

| Тест | Сутки завершения | Принято | Не принято |
| --- | --- | --- | --- |
| `test_minimum` | 1 | 1 | 0 |
| `test_empty` | 3 | 0 | 2 |
| `test_max_rooms` | 1 | 100 | 0 |
| `test_max_queue` | 100 | 100 | 0 |
| `test_max_stay` | 10001 | 2 | 0 |
| `test_max_interval` | 10000 | 0 | 2 |

Выводы и логи сохраняются в `results/named`, `results/unnamed` и `results/independent`. Для независимой версии общий вывод находится в `output.txt`, сообщения отдельных программ – в `worker_*.txt`. Результаты и исполняемые файлы исключены из Git.
