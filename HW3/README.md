## 1. Условие задачи

В гостинице имеется ограниченное количество одноместных номеров. Клиенты прибывают через случайные интервалы и запрашивают номер на заданное число условных суток. Администратор назначает свободный номер. Если номера заняты, клиент ожидает в общей очереди. После выезда номер получает следующий ожидающий клиент.

Программа должна показывать прибытие и запрос номера, постановку в очередь, назначение номера, заселение, каждый завершённый период проживания и выезд. Один номер не может быть занят двумя клиентами, а клиент не может занимать два номера. После прекращения приёма уже принятые клиенты должны завершить проживание.

В обеих версиях один родительский процесс создаёт дочерние процессы через `fork`. Обмен данными идёт через разделяемую память POSIX. В `hotel.c` используются именованные POSIX-семафоры (4–5 баллов), а в дополнительной программе `hotel_unnamed.c` – неименованные семафоры в общей памяти (6 баллов). Логика гостиницы и формат ввода одинаковые.

## 2. Участники и общие данные

| Участник | Представление | Действия |
| --- | --- | --- |
| Координатор | Родительский процесс, `main` | Читает данные, создаёт ресурсы и детей, продвигает условное время, следит за завершением и сохраняет статистику. |
| Администратор | Один дочерний процесс, `administrator` | Обрабатывает очередь, выбирает свободные номера и уведомляет клиентов о назначении. |
| Каждый клиент | Отдельный дочерний процесс, `client` | Прибывает, запрашивает номер, ожидает, заселяется, учитывает проживание и выезжает. |

При успешном запуске создаётся `client_count + 1` дочерних процессов. Вместе с родителем их `client_count + 2`. Потоки через `pthread_create` не создаются.

Общие данные собраны в `struct SharedState`: массивы `clients`, `rooms`, `queue`, границы очереди `head` и `tail`, условное время, статистика, признак остановки и счётчики обработки событий. Состояния клиента сохранены из `HW2`: `NOT_ARRIVED`, `WAITING`, `ASSIGNED`, `LIVING`, `LEFT`, `REJECTED`.

Память создаётся через `shm_open`, размер задаётся через `ftruncate`, отображение выполняется через `mmap` с `MAP_SHARED`. Дети наследуют это отображение после `fork` и видят изменения общих данных. Указатели на семафоры и массив PID находятся в обычной памяти процесса; в общую структуру они не записываются.

В `hotel_unnamed.c` в `SharedState` добавлен массив `sem_t semaphores[SEM_COUNT]`. Сами семафоры находятся в общей памяти, а локальный массив `events` хранит указатели на них.

## 3. Синхронизация и правила модели

| Семафор | Начальное значение | Назначение |
| --- | --- | --- |
| `ROOM_LOCK` | 1 | Защита общих данных и вывода событий. В критической секции находится один процесс. |
| `ADMIN_EVENT` | 0 | Уведомления администратора о запросах, освобождении номеров и остановке. |
| Семафор каждого клиента | 0 | Уведомления о прибытии, назначении номера, новых сутках и остановке. |
| `DAY_DONE` | 0 | Уведомление родителя о завершении событий текущих суток. |

В `hotel.c` семафоры создаются через `sem_open`; имена содержат PID родителя. В `hotel_unnamed.c` используется `sem_init` с `pshared = 1`, чтобы семафоры работали между процессами. Они создаются до `fork`. В обеих программах ожидание выполняется через `sem_wait`, уведомление – через `sem_post`. Каждый запуск создаёт свою общую память, поэтому запуски не мешают друг другу.

На каждых сутках родитель уведомляет прибывающих и проживающих клиентов. Клиент самостоятельно добавляет запрос в очередь; администратор извлекает запросы по FIFO и назначает свободные номера. Назначение сразу резервирует номер в `rooms`, после чего клиент подтверждает заселение. При выезде клиент освобождает номер и будит администратора.

Счётчик `pending_work` учитывает незавершённые события. Следующие сутки начинаются только после их обработки. Порядок действий разных участников внутри суток определяется планировщиком процессов. При одинаковом времени прибытия FIFO соответствует фактической постановке в очередь, а не индексу клиента.

Время начинается с нуля. Принимаются клиенты с `arrival_time < reception_end`. После закрытия приёма очередь продолжает обслуживаться. Срок проживания считается от `check_in_time`; ожидание в него не входит. Выезд происходит при `current_time - check_in_time == stay_days`.

Нулевой интервал допускает одновременное прибытие. Используется `srand(1)`, но порядок исполнения процессов не фиксируется. Зона ожидания рассчитана на всех клиентов. Сохранены функции `read_int`, `find_free_room`, `check_in` и основная логика `HW2`.

## 4. Ввод и запуск

Программа считывает числа из `stdin` в следующем порядке:

| Параметр | Диапазон |
| --- | --- |
| Количество номеров | 1–100 |
| Количество клиентов | 1–100 |
| Минимальный интервал прибытия | 0–10000 |
| Максимальный интервал прибытия | От минимального до 10000 |
| Момент прекращения приёма | 1–10000 |
| Задержка между условными сутками | 0–5 реальных секунд |
| Срок проживания каждого клиента | 1–10000 условных суток |

Основная среда выполнения – Linux. Команды из каталога `HW3`:

```sh
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread hotel.c -o hotel -lrt
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread hotel_unnamed.c -o hotel_unnamed -lrt
./hotel
```

Ввод из файла:

```sh
./hotel < tests/test_cutoff.txt
./hotel_unnamed < tests/test_cutoff.txt
```

На macOS поддерживается только вариант с именованными семафорами. Для второго нужен Linux: `sem_init` на macOS возвращает ошибку `ENOSYS`. Команда сборки первого варианта выполняется без `-lrt`:

```sh
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread hotel.c -o hotel
```

Сборка через CMake:

```sh
cmake -S . -B build
cmake --build build
./build/hotel < tests/test_minimum.txt
```

В Linux CMake также создаёт `build/hotel_unnamed`.

Автоматические проверки требуют Python 3:

```sh
sh run_tests.sh
```

Скрипт сам выбирает параметры сборки для ОС и переходит в свой каталог. В Linux проверяются обе программы, на macOS – только именованные семафоры. Одну версию можно выбрать командой `sh run_tests.sh named` или `sh run_tests.sh unnamed`. Из корня репозитория скрипт запускается как `sh HW3/run_tests.sh`.

## 5. Завершение и очистка ресурсов

Нормальное завершение происходит, когда все клиенты находятся в `LEFT` или `REJECTED`. Если все клиенты уже обслужены, модель может закончиться раньше `reception_end`. Если очередь ещё не пуста, обслуживание продолжается после закрытия приёма.

Ctrl+C посылает `SIGINT`. Родитель также обрабатывает `SIGTERM`. Дочерние процессы игнорируют эти два сигнала: остановкой всей модели управляет родитель через общий признак `stopping` и пробуждение семафоров. Это позволяет корректно обработать сигнал как одному родителю, так и всей группе процессов из терминала. Обработчик сигнала только устанавливает флаг.

Родитель собирает завершившихся детей через `waitpid`. Неожиданное завершение ребёнка обнаруживается по его статусу. В Linux родитель использует ограниченное по времени ожидание `sem_timedwait`; на macOS для этого используется `sem_trywait` с короткой паузой. Поэтому потеря уведомления при аварии ребёнка не оставляет родителя в бесконечном ожидании.

При аварии или частичной ошибке `fork` оставшиеся дочерние процессы принудительно завершаются и собираются через `waitpid`. На аварийном пути родитель не требует освобождения бинарного семафора: погибший ребёнок мог оставить его занятым.

После остановки детей родитель сохраняет статистику в консоль и `hotel.log`. В `hotel.c` процессы закрывают свои семафоры через `sem_close`, а родитель удаляет имена через `sem_unlink`. В `hotel_unnamed.c` только родитель вызывает `sem_destroy`, когда все дети уже завершились. Затем процессы освобождают отображение памяти, а родитель удаляет её имя через `shm_unlink`. При ошибке подготовки удаляются только успешно созданные ресурсы этого запуска.

| Ситуация | Код завершения |
| --- | --- |
| Нормальное завершение | 0 |
| Ошибка ввода, IPC, создания ребёнка, авария ребёнка или ошибка записи лога | 1 |
| Остановка родителя через `SIGINT` | 130 |
| Остановка родителя через `SIGTERM` | 143 |

Ошибка имеет приоритет перед кодом сигнала. При прерывании до завершения ввода новый лог не создаётся. При остановке запущенной модели лог показывает фактически завершённые проживания, оставшуюся очередь и занятые номера.

Очистка предусмотрена для нормального завершения, `SIGINT`, `SIGTERM` и обрабатываемых ошибок. Принудительное уничтожение самого родителя через неперехватываемый `SIGKILL` не является штатным способом остановки.

## 6. Результаты проверки

8 ноября 2026 года выполнены проверки на Linux ARM64 в Debian с GCC и на macOS ARM64 с Apple clang. Для `hotel.c` прошли **57 проверок в Linux** и **56 в macOS**. Для `hotel_unnamed.c` прошли **58 проверок в Linux**. Проверка структуры дочерних процессов через `/proc` выполняется только в Linux. Сборка через CMake проверена с флагами `-Wall -Wextra -Wpedantic -Werror`.

Основой служат 47 сценариев `HW2`: 17 файловых наборов, 7 дополнительных проверок ввода, 20 нагрузочных сценариев и 3 проверки сигналов. Разбор событий проверяет FIFO, отсутствие двойного назначения номера, полный срок проживания, границу приёма и соответствие итоговой статистики событиям.

| Сценарий | Сутки завершения | Принято | Не принято |
| --- | --- | --- | --- |
| `test_minimum` | 1 | 1 | 0 |
| `test_cutoff` | 5 | 2 | 1 |
| `test_empty` | 3 | 0 | 2 |
| `test_max_rooms` | 1 | 100 | 0 |
| `test_max_queue` | 100 | 100 | 0 |
| `test_max_stay` | 10001 | 2 | 0 |
| `test_max_interval` | 10000 | 0 | 2 |

В `test_cutoff` первый клиент проживает с суток 1 до суток 4, второй ожидает и проживает с суток 4 до суток 5. Прибытие третьего запланировано ровно на момент закрытия, поэтому он не принимается. Итоговый лог:

```text
Моделирование завершено на сутках: 5
Всего приняли клиентов: 2.
Полностью завершили проживание: 2.
Не успели принять клиентов: 1.
Ожидают заселения: 0.
Занятых номеров: 0.
```

Дополнительные проверки для этой версии:

| Проверка | Подтверждённое поведение |
| --- | --- |
| `SIGINT` всей группе процессов | Код 130, дети завершены, итог сохранён. |
| `SIGTERM` всей группе процессов | Код 143, дети завершены, итог сохранён. |
| `SIGINT` при вводе | Код 130, программа не остаётся ждать ввод. |
| Два параллельных запуска | Данные и IPC-ресурсы сеансов не пересекаются. |
| Ошибка создания `hotel.log` | Код 1, общие ресурсы удалены. |
| Ошибка третьего вызова `fork` | Уже созданные дети остановлены и собраны, ресурсы удалены. |
| Ошибка третьего `sem_open` или `sem_init` | Ранее созданные семафоры и память удалены. |
| Удаление неименованных семафоров | `sem_destroy` вызывается родителем только для созданных семафоров и до освобождения памяти. |
| Ошибка `ftruncate` | Созданный объект памяти удалён. |
| Ошибка `mmap` | Созданный объект памяти удалён. |
| Аварийное завершение ребёнка, Linux | Для трёх клиентов обнаружены четыре дочерних процесса; после принудительной остановки одного родитель возвращает 1, остальных детей и зомби не остаётся. |

После запусков тесты проверяют невозможность открыть использованные имена IPC без создания новых объектов, а также отсутствие оставшихся процессов тестовой группы. Ошибки системных вызовов моделируются отдельным тестовым бинарником с подменами из `tests/failures.c`; основная программа специальных режимов отказа не содержит.

Выводы сохраняются в `results/named/<название>/output.txt` и `results/unnamed/<название>/output.txt`, итоговые логи – рядом в `hotel.log`. Результаты, исполняемые файлы и каталоги сборки исключены из Git. Порядок одновременно прибывших клиентов может отличаться между запусками, поэтому фиксированный полный текст вывода не используется как эталон.
