## 1. Условие и цель работы

В гостинице имеется ограниченное количество одноместных номеров. Клиенты прибывают через случайные интервалы и запрашивают номер на заданное число условных суток. Администратор предоставляет свободный номер. Если свободных номеров нет, клиент ожидает в общей очереди. После завершения проживания номер освобождается и может быть передан следующему ожидающему.

Необходимо отображать прибытие и запрос номера, постановку в очередь, назначение номера, заселение, каждый завершённый период проживания, выезд и передачу освободившегося номера. Один номер не может быть назначен двум клиентам одновременно, а один клиент не может занимать несколько номеров. Срок проживания каждого заселённого клиента должен учитываться полностью.

Задание №2 развивает последовательную реализацию из `HW1`. Цель работы – представить администратора и клиентов отдельными потоками, организовать их взаимодействие с помощью мьютекса и семафоров и обеспечить корректное завершение программы. Реализация выполнена на языке C с использованием libc, POSIX API и библиотеки `pthread`. Целевая ОС – Linux; программа также проверена на macOS.

## 2. Правила реализованной модели

Время начинается с нуля и изменяется на одни условные сутки. Параметр `reception_end` задаёт момент прекращения приёма новых клиентов. Принимаются только клиенты с временем прибытия строго меньше `reception_end`. Прибытие ровно в момент закрытия уже не принимается. После закрытия гостиница продолжает обслуживать принятую очередь и проживающих, поэтому итоговое время может превышать `reception_end`.

Интервал между соседними прибытиями вычисляется выражением:

```c
arrival_min + rand() % (arrival_max - arrival_min + 1)
```

Интервал прибавляется к моменту предыдущего прибытия. Для первого клиента отсчёт идёт от нуля. При нулевом интервале несколько клиентов могут прибыть одновременно. Времена прибытия вычисляются в `main` до создания потоков. Используется `srand(1)`: последовательность повторяется в рамках одной реализации генератора, но может отличаться между платформами.

Стратегия заселения – FIFO: первым обслуживается тот, кто раньше поставил запрос в очередь. При одинаковом времени прибытия порядок определяется фактической постановкой в очередь потоками клиентов. В отличие от `HW1`, порядок по индексам клиентов не гарантируется.

Каждый запрос поступает в общую очередь администратора. Если номер свободен, запрос может быть обслужен на тех же условных сутках; если все номера заняты, клиент остаётся ждать. Свободный номер выбирается первым при просмотре массива `rooms`. Ожидание в очереди не включается в срок проживания.

Отдельного ограничения зоны ожидания нет: массив очереди вмещает всех клиентов модели. Максимальное количество номеров и клиентов равно 100. FIFO фиксирована в программе и не запрашивается при вводе.

## 3. Представление участников и данных

Программа работает в одном процессе. При успешном запуске создаются `client_count` потоков клиентов и один поток администратора. Вместе с главным потоком в программе имеется `client_count + 2` потока. Номера и очередь представлены общими данными, поскольку сами по себе действий не выполняют.

| Участник | Представление | Выполняемые действия |
| --- | --- | --- |
| Главный поток | `main` | Ввод параметров, подготовка данных, создание потоков, продвижение условного времени, остановка и сохранение результатов. |
| Администратор | Поток с функцией `administrator` | Ожидание уведомлений, поиск свободных номеров, извлечение запросов из очереди, назначение номеров и пробуждение клиентов. |
| Клиент | Отдельный поток с функцией `client` | Прибытие, запрос номера, ожидание назначения, подтверждение заселения, учёт проживания и выезд. |

### Основные данные

| Объект | Назначение |
| --- | --- |
| `clients` | Массив структур `Client`: время прибытия, срок проживания, время заселения, номер, состояние и семафор каждого клиента. |
| `rooms` | Массив индексов клиентов. Значение `-1` означает свободный номер. Назначенный, но ещё не подтверждённый клиентом номер тоже считается занятым. |
| `queue` | Массив индексов клиентов, ожидающих назначения номера. Каждый клиент добавляется не более одного раза. |
| `head`, `tail` | Начало очереди и место добавления следующего запроса. При `head == tail` очередь пуста. |
| `accepted`, `completed` | Количество принятых клиентов и количество клиентов, полностью завершивших проживание. |
| `current_time` | Текущие условные сутки. Изменяются главным потоком после обработки событий предыдущего шага. |
| `pending_work` | Количество событий, которые ещё должны обработать потоки. Ожидающий свободного номера клиент сам по себе не удерживает этот счётчик. |
| `work_pending`, `admin_pending` | Признаки уже запланированной работы клиента или администратора. Предотвращают дублирование уведомлений об одной ожидающей обработке. |
| `stopping` | Общий признак завершения рабочих потоков. |

Состояния клиента:

| Состояние | Значение |
| --- | --- |
| `NOT_ARRIVED` | Клиент ещё не прибыл. |
| `WAITING` | Запрос находится в очереди администратора. |
| `ASSIGNED` | Администратор зарезервировал номер, клиент ещё не подтвердил заселение. |
| `LIVING` | Клиент проживает в назначенном номере. |
| `LEFT` | Клиент прожил весь заказанный срок и выехал. |
| `REJECTED` | Приём закрыт, клиент не был принят. |

Обычный путь клиента: `NOT_ARRIVED → WAITING → ASSIGNED → LIVING → LEFT`. Для клиента, не прибывшего до закрытия, выполняется переход `NOT_ARRIVED → REJECTED`. При прерывании программы промежуточное состояние не заменяется на `LEFT`: незавершённое проживание не считается завершённым.

## 4. Взаимодействие потоков и синхронизация

Для защиты общих данных используется `pthread_mutex_t mutex`. Изменения очереди, распределения номеров, состояний клиентов и счётчиков работы выполняются под этим мьютексом. Сообщения рабочих потоков о событиях выводятся в той же критической секции, поэтому строки разных событий не смешиваются.

Ожидание событий организовано через POSIX-семафоры:

| Семафор | Кто ожидает | Назначение |
| --- | --- | --- |
| `clients[i].event` | Поток клиента `i` | Уведомление о времени прибытия, назначении номера, новых сутках проживания или остановке. |
| `admin_event` | Поток администратора | Уведомление о поступлении запроса, освобождении номера, очередном шаге модели или остановке. |
| `day_done` | Главный поток | Уведомление о завершении обработки всех запланированных событий текущих суток. |

Семафоры создаются функцией `sem_open` с начальным значением 0. Имена содержат PID процесса и индекс семафора. После создания имя сразу удаляется через `sem_unlink`, а открытый семафор используется до вызова `sem_close`. Такая реализация используется и в Linux, и в macOS.

Рабочие потоки вызывают `sem_wait` до захвата мьютекса. Если событий нет, поток ожидает на семафоре, не занимая мьютекс. `sem_post` уведомляет нужный поток. FIFO обеспечивается массивом `queue`, а не порядком пробуждения потоков операционной системой.

### Обработка одних условных суток

1. Главный поток выводит текущие сутки и уведомляет прибывающих и проживающих клиентов. При достижении `reception_end` ещё не прибывшие клиенты переводятся в `REJECTED` и получают уведомление для завершения своих потоков.
2. Прибывший клиент выводит запрос, добавляет себя в очередь и будит администратора.
3. Администратор извлекает запросы в порядке FIFO, пока есть свободные номера. Функция `check_in` резервирует номер, задаёт `check_in_time`, устанавливает `ASSIGNED` и будит соответствующего клиента.
4. Клиент подтверждает заселение и переходит в `LIVING`. На следующих сутках он вычисляет `current_time - check_in_time` и выводит завершённый период проживания. При достижении `stay_days` освобождает номер, переходит в `LEFT` и уведомляет администратора.
5. После каждого обработанного события уменьшается `pending_work`. Когда счётчик становится равен нулю, последний обработавший событие поток уведомляет `main` через `day_done`.
6. Главный поток проверяет условие завершения. Если работа продолжается, выполняет `nanosleep` с заданной задержкой и переходит к следующим суткам.

Пункты описывают зависимости между действиями. Фиксированного порядка исполнения всех потоков внутри одних суток нет. Например, события разных проживающих клиентов могут выводиться в разном порядке. Главный поток не переходит к следующим суткам, пока не обработаны текущие события и связанные с ними назначения номеров.

Время назначения номера и подтверждения заселения совпадает в условных сутках: между этими событиями счётчик работы ещё не обнулён. Поэтому срок проживания отсчитывается полностью даже при нулевой реальной задержке.

### Поддержание инвариантов

| Инвариант | Как обеспечивается |
| --- | --- |
| Один номер назначен не более чем одному клиенту. | Поиск и резервирование номера выполняются администратором под мьютексом; при назначении запись `rooms` сразу перестаёт быть свободной. |
| Клиент занимает не более одного номера. | Клиент добавляется в очередь один раз; после извлечения запрос больше не участвует в назначениях. |
| Число занятых номеров не превышает вместимость. | Назначается только существующий номер со значением `-1`. |
| Номер повторно назначается после освобождения. | Клиент очищает запись `rooms` под мьютексом, затем уведомляет администратора. |
| Срок проживания учитывается полностью. | Время увеличивается после обработки текущих событий; выезд происходит при `current_time - check_in_time == stay_days`. |
| Сохраняется FIFO. | Администратор извлекает только `queue[head]` и последовательно увеличивает `head`. |

## 5. Консольный интерфейс и запуск

Параметры считываются из стандартного потока `stdin`. Их можно вводить вручную или передавать перенаправлением из текстового файла. Рекомендуется вводить каждое число с новой строки.

| Порядок | Параметр | Допустимые значения |
| --- | --- | --- |
| 1 | Количество номеров | 1–100 |
| 2 | Количество клиентов | 1–100 |
| 3 | Минимальный интервал прибытия | 0–10000 условных суток |
| 4 | Максимальный интервал прибытия | От минимального интервала до 10000 |
| 5 | Момент прекращения приёма | 1–10000 условных суток |
| 6 | Задержка между условными сутками | 0–5 реальных секунд |
| 7 и далее | Срок проживания каждого клиента | 1–10000 условных суток |

Функция `read_int` читает токен через `scanf`, проверяет его длину, преобразует через `strtol` и проверяет остаток токена и диапазон. Пустой ввод, отсутствие обязательного числа, посторонние символы, слишком длинный токен и выход за диапазон приводят к сообщению об ошибке и прекращению ввода.

Задержка влияет на скорость отображения событий. Значение 0 позволяет выполнять модель без намеренной паузы между сутками. Очерёдность обработки событий при этом по-прежнему согласуется семафорами.

### Сборка и ручной запуск

Нужен компилятор C с поддержкой POSIX Threads. Следующие команды выполняются из каталога `HW2`:

```sh
gcc -std=c11 -Wall -Wextra -Wpedantic -pthread hotel.c -o hotel
./hotel
```

Для ввода из подготовленного файла:

```sh
./hotel < tests/test_cutoff.txt
```

Для запуска всех автоматических проверок дополнительно нужен Python 3:

```sh
sh run_tests.sh
```

Скрипт сам переходит в каталог `HW2`, собирает программу и запускает проверки. Из корня репозитория его можно вызвать командой `sh HW2/run_tests.sh`.

### Сборка через CMake

Нужен CMake версии 3.16 или новее. Команды из `HW2`:

```sh
cmake -S . -B build
cmake --build build
./build/hotel < tests/test_minimum.txt
```

### Пример исходных данных

Содержимое `tests/test_cutoff.txt`:

```text
1
3
1
1
3
0
3
1
1
```

Здесь один номер, три клиента, интервал прибытия ровно одни сутки, приём до суток 3 и нулевая задержка. Сроки проживания клиентов: 3, 1 и 1 сутки.

Первый клиент прибывает на сутках 1 и выезжает на сутках 4. Второй прибывает на сутках 2 и ждёт освобождения номера, затем проживает до суток 5. Третий должен прибыть на сутках 3, когда приём уже закрыт, и не принимается.

## 6. Завершение работы и итоговый лог

При нормальном завершении все клиенты находятся в состояниях `LEFT` или `REJECTED`. Очередь пуста, все номера свободны. Если все клиенты уже обслужены, программа может завершиться раньше заданного момента закрытия приёма.

Главный поток устанавливает `stopping`, уведомляет рабочие потоки, ожидает созданные потоки через `pthread_join`, выводит статистику и сохраняет её в `hotel.log`. После этого закрываются семафоры и уничтожается мьютекс.

Файл лога создаётся через `creat`, записывается через `dprintf` и закрывается через `close`. Он находится в текущем рабочем каталоге запуска. При сохранении нового результата прежнее содержимое заменяется. Подробные события идут в консоль; `hotel.log` содержит итоговую статистику.

Пример результата для `test_cutoff.txt`:

```text
Моделирование завершено на сутках: 5
Всего приняли клиентов: 2.
Полностью завершили проживание: 2.
Не успели принять клиентов: 1.
Ожидают заселения: 0.
Занятых номеров: 0.
```

«Всего приняли клиентов» учитывает поступившие в очередь запросы, включая ещё не заселённых клиентов. «Полностью завершили проживание» учитывает только выехавших после полного срока. При нормальном завершении эти числа равны. Число непринятых вычисляется как `client_count - accepted`.

### Прерывание пользователем

Предусмотрены `SIGINT` и `SIGTERM`. При ручном запуске Ctrl+C посылает `SIGINT`. Рабочие потоки наследуют блокировку этих сигналов; обрабатывает их главный поток. Обработчик только записывает номер сигнала в `stop_requested`, не выполняет вывод и не захватывает мьютекс.

Главный поток прекращает продвижение времени, устанавливает признак остановки и будит также клиентов, ожидающих прибытия или номера. После `pthread_join` сохраняется статистика на момент остановки. Проживающие не записываются как выехавшие: в логе остаются количество занятых номеров и длина очереди.

Если прерывание произошло ещё при вводе параметров, программа завершает ввод; новый итоговый лог не создаётся, поскольку модель ещё не запущена.

| Ситуация | Результат | Код завершения |
| --- | --- | --- |
| Все принятые клиенты завершили проживание, остальные отклонены. | Итоговая статистика в консоли и `hotel.log`. | 0 |
| Некорректный или неполный ввод. | Сообщение об ошибке; новый лог не создаётся. | 1 |
| Ошибка подготовки ресурсов, создания потока или работы с логом. | Сообщение об ошибке. При частичном создании потоков уже созданные потоки останавливаются и ожидаются. | 1 |
| `SIGINT` во время работы. | Остановка потоков и сохранение текущей статистики, если запись лога доступна. | 130 |
| `SIGTERM` во время работы. | Остановка потоков и сохранение текущей статистики, если запись лога доступна. | 143 |

Если при завершении возникает ошибка, например невозможность создать лог, программа возвращает 1. Неожиданная ошибка `sem_wait` или `sem_post` приводит к немедленному выходу с кодом 1; сохранение итогового лога на этом аварийном пути не гарантируется.

### Проверяемые свойства

Файл [tests/check_tests.py](tests/check_tests.py) разбирает события и восстанавливает состояние номеров, очереди и клиентов. Проверяются:

- назначение только свободных номеров и отсутствие двух номеров у одного клиента;
- соблюдение FIFO по фактическому порядку постановки запросов в очередь;
- подтверждение заселения после назначения номера;
- каждый завершённый период проживания и полный срок перед выездом;
- обслуживание очереди после прекращения приёма;
- отсутствие ожидающих при свободных номерах после обработки событий суток;
- правильная граница приёма и моменты прибытия в сценариях с фиксированным интервалом;
- соответствие итогового лога событиям;
- коды завершения при неверном вводе и прерывании сигналом.

Обычный запуск ограничен в тестовом скрипте 60 секундами. В проверках сигналов на запуск модели отводится до 10 секунд, а после отправки сигнала на завершение – до 3 секунд. Превышение времени считается ошибкой проверки.

### Скрипт запуска и сохраняемые результаты

[run_tests.sh](run_tests.sh) собирает программу и передаёт проверку Python-скрипту:

```sh
#!/bin/sh

# Скрипт можно запускать из любой папки. Для проверки вывода нужен Python 3.
cd "$(dirname "$0")" || exit 1
compiler=${CC:-gcc}
"$compiler" -std=c11 -Wall -Wextra -Wpedantic -pthread hotel.c -o hotel || exit 1
python3 tests/check_tests.py ./hotel
```

Для каждого сценария создаётся отдельный каталог `results/<название>`. В `output.txt` сохраняется полный вывод программы вместе с сообщениями об ошибках, а в `hotel.log` – её итоговая статистика, если моделирование было запущено. Перед обычным тестом старый лог этого сценария удаляется, чтобы не использовать результат предыдущего запуска.

Ожидаемый итог формируется в проверяющем скрипте по разобранным событиям. Фиксированные эталонные последовательности строк из `HW1` не используются. При провале проверки скрипт завершается с ненулевым кодом; сообщение об успехе всех тестов появляется только после прохождения всего набора.

## 8. Ограничения реализации

Модель рассчитана на конечное количество клиентов, целые условные сутки и максимум 100 номеров и 100 клиентов. Неограниченный режим и отдельная настройка вместимости зоны ожидания не реализованы. Параметры модели задаются через `stdin`; разбора аргументов командной строки и конфигурационного файла нет.

Значение `reception_end` ограничивает приём новых клиентов, а не полную длительность работы. При нормальном завершении все принятые клиенты обслуживаются полностью. Прерывание пользователем намеренно останавливает модель с незавершёнными проживаниями и отражает это в статистике.

Модель использует общий счётчик условного времени: потоки обрабатывают события асинхронно внутри шага, а переход между сутками согласован через `day_done`. Реальные задержки планировщика ОС не превращаются в дополнительные условные сутки.

Фиксированный `srand(1)` не задаёт порядок выполнения потоков. Совпадение полного вывода между запусками и платформами не гарантируется. При одновременном прибытии одинаковые входные данные могут давать разные допустимые порядки заселения.

Лог содержит только итоговую статистику. Для сохранения полной последовательности событий можно перенаправить стандартный вывод в файл; тестовый скрипт делает это автоматически. Вторая реализация с другими средствами синхронизации вместо семафоров не создавалась.

Проведённые тесты подтверждают поведение на проверенных сценариях. Проверка с ThreadSanitizer не выявила гонок в выполненных запусках, но не является доказательством отсутствия ошибок при всех возможных расписаниях потоков. Производительность и статистические свойства генератора случайных чисел отдельно не исследовались.
